# Payments: автоматическое и ручное подтверждение

Новый режим предназначен для клиентских платежей Яндекс Игр (`useBackend = false`).
Серверная обработка и другие платформы сохраняют свои существующие механизмы.

## Что сделано в текущем обновлении

Цель обновления — исправить опасные места и дать ручной API без обязательного
переписывания существующих игр.

- Отказы `getCatalog` и `getPurchases` при инициализации обрабатываются общей
  цепочкой промисов. `InitPayments` завершается с `NO_DATA` при ошибках SDK;
  ошибка обратного вызова Unity также не оставляет инициализацию незавершённой.
- Добавлена обработка отказов получения и подтверждения покупок.
- В автоматическом режиме событие выдачи отправляется перед запросом подтверждения.
- Новая покупка обрабатывается по транзакции из результата `purchase()`, без
  повторного поиска и списания всех покупок с тем же ID товара.
- Добавлена защита по токену от одновременного списания и повторной выдачи
  в пределах текущего сеанса. Эта защита не заменяет сохранённый журнал токенов.
- Добавлены `AutoConsume = true`, ручной API транзакций и базовая симуляция в редакторе.

Проверки платежного API включают вызовы через `.jslib`; C#-часть проверяется
компиляцией основной, редакторной и Player-сборок через MSBuild. Полный
WebGL-билд и проверка на реальном SDK площадки пока не выполнены.

Пример собственной обработки упрощён до одного `ManualPaymentsExample.cs`.
Он использует `YG2.saves` и новый `SaveProgress(Action<bool>)` модуля Storage.
Отдельное хранилище примера и его JS-мост удалены; ожидание SDK и корутина
из примера убраны. Описание для сайта: `Docs/PaymentsCustomImplementation.md`.
Контракт callback: `Docs/StorageSaveCallback.md`.

## Совместимость

В настройках Payments добавлено поле `AutoConsume`, по умолчанию `true`.
Значение записывается в WebGL-шаблон при сборке: после изменения требуется пересобрать игру.

При `AutoConsume = true` сохраняется прежний API: `BuyPayments` вызывает
`onPurchaseSuccess(id)` и затем подтверждает покупку. Компонент `ConsumePurchasesYG`
восстанавливает оставшиеся покупки. Повторная обработка одного токена в текущем
сеансе не вызывает повторную выдачу; одновременные подтверждения разделяют один запрос SDK.
После отказа подтверждения его можно повторить. Отказ подтверждения оплаченной покупки
не вызывает `onPurchaseFailed`: это событие относится к отказу самой покупки.

Автоматический режим не ожидает завершения пользовательского асинхронного сохранения.
Для подтверждения строго после сохранения используйте ручной режим.

## Ручной режим

Отключите `AutoConsume` до сборки игры.

- `YG2.BuyPayments(id)` открывает оплату как раньше. При успехе вызывается
  **только** `YG2.onPurchaseReceived`, без списания токена и без старого события
  `onPurchaseSuccess`.
- `ConsumePurchasesYG` не запускает автоматическое восстановление клиентских покупок.
- Существующие явно вызванные `ConsumePurchases` и `ConsumePurchaseByID` по-прежнему
  списывают покупки. Не используйте их в ручном обработчике.

Данные отдельной транзакции находятся в `YG.Utils.Pay.PaymentTransaction`:

```csharp
public string productID;
public string purchaseToken;
```

Один товар может иметь несколько транзакций с разными токенами. Каталог
`YG2.purchases` и `PurchaseByID` остаётся отдельным API товаров; `consumed` не заменяет
список транзакций и не подходит для защиты от повторного начисления.

| Метод / событие | Назначение |
| --- | --- |
| `YG2.onPurchaseReceived` (`Action<PaymentTransaction>`) | Новая оплаченная покупка в ручном режиме |
| `YG2.GetPendingPurchases()` | Запросить оставшиеся покупки без выдачи и списания |
| `YG2.onGetPendingPurchases` (`Action<PaymentTransaction[]>`) | Результат запроса, включая пустой массив |
| `YG2.onGetPendingPurchasesFailed` (`Action<string>`) | Ошибка запроса |
| `YG2.ConsumePurchaseByToken(token)` | Подтвердить одну транзакцию |
| `YG2.onPurchaseConsumed` (`Action<string>`) | Успешное подтверждение, передаёт токен |
| `YG2.onPurchaseConsumeFailed` (`Action<string>`) | Отказ подтверждения, передаёт токен; причина записывается в консоль |

Подпишитесь на события до запросов. Отписывайтесь при отключении обработчика.
После готовности SDK и загрузки сохранения вызывайте `GetPendingPurchases()` при
каждом запуске игры. Сам запрос не вызывает `onPurchaseReceived` — обработайте
полученный массив тем же кодом выдачи.

Для используемой покупки:

1. Проверьте, был ли токен уже обработан, включая параллельные операции в текущем сеансе.
2. Для нового токена выдайте награду и сохраните её **вместе с отметкой токена**.
3. Дождитесь успешного сохранения.
4. Вызовите `ConsumePurchaseByToken(purchase.purchaseToken)`.
5. При отказе подтверждения повторите подтверждение позже, не выдавая товар повторно.

Подтверждение по токену не вызывает события выдачи. Для постоянного товара
восстановите право на товар по списку покупок и **не списывайте токен**.

## Unity Editor и ограничения

В ручном режиме успешная симуляция оплаты создаёт токен. Новые методы позволяют
получить и подтвердить эти симулированные покупки. Список существует только в текущем
сеансе Play Mode; это не эмуляция серверного хранения или сетевых ошибок Яндекса.

Новый токеновый API не обходит серверную проверку: при включённом backend он возвращает
ошибку. `AutoConsume` не меняет серверный протокол подтверждения.

Проверка JS-логики без Unity: `node --test Tests/Payments.test.cjs`.
Перед выпуском проверьте в черновике Яндекс Игр покупку, восстановление после
перезагрузки, отказ сети при подтверждении и постоянный товар без списания.

## Следующее мажорное обновление: направление работы

### Незавершённая серверная обработка

Backend платежей находится в разработке и пока не анонсируется пользователям.
Перед его выпуском необходимо закончить серверную часть, проверить проверку
подписей, восстановление заказов, сохранение награды и подтверждение покупки,
а также защиту от повторной обработки запросов. После этого провести сквозные
проверки на площадке, включая сетевые отказы и повторный запуск игры.

Текущие клиентские примеры не требуют включения `useBackend`. Упоминания этой
неопубликованной функции не добавлять в раздел документации для сайта
`Docs/PaymentsCustomImplementation.md` до её готовности.

### Переработка основного API

Планируется заменить старую совмещённую систему выдачи и консумирования новым
основным сценарием. В мажорной версии допустимы изменения API, требующие
обновления кода игр. Точные имена методов, схема миграции и сроки пока не утверждены.

При проектировании новой системы необходимо:

- Разделить получение оплаченной транзакции, выдачу и сохранение награды,
  подтверждение конкретной покупки по токену.
- Предусмотреть подтверждение только после успешного сохранения, а не после
  простого вызова события выдачи.
- Обрабатывать восстановление по отдельным транзакциям и предусмотреть защиту
  от повторной выдачи после перезапуска или повторного получения покупки.
- Разделить используемые и постоянные товары: постоянные восстанавливаются
  без списания токена.
- Переработать готовые компоненты, примеры и документацию под новый сценарий.
- Определить согласованное поведение клиентской и серверной обработки.

Старый автоматический сценарий сохранён в текущем обновлении ради совместимости.
Его дальнейшая замена относится к мажорному обновлению; перечисленные выше
возможности будущей системы не следует считать уже реализованными гарантиями.
